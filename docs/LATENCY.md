# 本地运行时 late 率偏高

本地用 `MODEL=jev DRY_RUN=true` 跑起来之后，看板上大部分区块是琥珀色的 LATE，成交流水很稀疏，`totals.lateBlocks` 长期占 `totals.blocks` 的一半以上。

这不是模型判断出错，也不是代码有 bug。原因是**这台机器到 Monad 节点和到 AI 服务的地理距离太远**，而主循环的设计决定了它一旦赶不上，就整块放弃，不排队。

## late 的判定

判定在 `src/trader.ts`，主循环一开始就检查 `busy`：

    if (this.busy) {
      this.totals.lateBlocks++;
      ...emit(block, lastBook, null, null, true);   // late = true
      return;
    }

`busy` 在一次区块处理的开头置位，在 `finally` 里清除。所以 **`late` 的含义是：新区块到达的时候，上一次的「读盘口加问模型加下单」还没跑完**。

设计上是单飞（同一时刻只允许一笔在途）且 fire-and-forget，**不排队、不并发**。赶不上就发一个 `hold` 事件，等下一个区块。这个设计同时保证了 nonce 单调。

于是问题简化成一句话：**干一次活要多久，比区块间隔长多少。**

## 实测

日志里有每一次决策的 `read` 和 `loop` 明细。取 1651 个样本：

| 阶段 | p50 | p90 | max | avg |
|---|---|---|---|---|
| 读盘口 | 252 ms | 267 ms | 633 ms | 249 ms |
| 模型推理 | 317 ms | 369 ms | 1221 ms | 325 ms |
| loop 合计 | 567 ms | 623 ms | 1450 ms | 574 ms |

区块间隔另外实测过：24.22 秒推进 80 个区块，**302.7 ms**，和代码里写死的 300 一致。

把 loop 耗时按 300 ms 的预算分档：

| loop 耗时 | 次数 | 占比 |
|---|---|---|
| 300 ms 以内 | 0 | 0.0% |
| 400 ms 以内 | 0 | 0.0% |
| 500 ms 以内 | 33 | 2.0% |
| 600 ms 以内 | 1315 | 79.6% |

**1651 次决策里，0 次在 400 ms 内跑完**，最快的一次也在 500 ms 以上。

这就决定了它的节奏。相邻两次决策之间的区块间隔分布是：2 个区块 1173 次，3 个区块 468 次。3793 个区块里完成 1651 次决策，**决策率 43.5%，也就是 56.5% 的区块是 late**。

这个数字不是「偶尔超时」，是结构性的：只要 loop 耗时落在 300 ms 到 600 ms 之间，就必然有一半以上的区块被跳过。

## 和已部署实例的对照

同一份代码、同一个 `jev-latest` 模型、同样是 dry run：

| | 本机 | 已部署实例 |
|---|---|---|
| late 率 | 56.3% | **6.75%** |
| 决策率 | 43.5% | **92.01%** |
| 累计区块 | 3793 | 944841 |

两个实例跑的东西完全一样，唯一的差别是所在网络的位置。作者的实例和链处在同一区域，两段往返都很短。

## 慢的是网络，不是算力

两段耗时都不是计算，是等待：

| | 本机实测 | 文档中的数字 | 倍数 |
|---|---|---|---|
| 读盘口 | 249 ms | 约 18 ms | 约 14 倍 |
| 模型推理 | 325 ms | 约 100 ms | 约 3 倍 |

README 的 300 毫秒预算一节说公开 RPC 读一次盘口约 18 ms，SPEC 说 Jev 模型约 100 ms。在本机测出来是 249 ms 和 325 ms。两段同时慢了几倍到十几倍，原因是一致的。

顺带说明：文档里那个「整个循环 p50 为 100 毫秒」的数字是 **mock 模型**跑出来的，其中 80 ms 是 mock 的推理替身。换成真实模型之后，推理这一段就从 80 ms 变成 325 ms，把它盖住的真相露出来了。

## 换更快的 RPC 不管用

逐个测过 Monad 的公开端点：`rpc.monad.xyz`、`rpc1/2/3.monad.xyz`、`monad-mainnet.drpc.org`、`monad-rpc.publicnode.com`、`1rpc.io/monad`，没有一个能把这 249 ms 压下来。

这里有个测量上的坑值得写下来：第一轮测试结果全部落在 0.5 到 1.5 秒，看起来更糟。原因是 `curl` 走了本机的一个 HTTP 代理，光 TLS 握手就占 384 ms，把每一个端点都等量拖慢了。**必须绕开代理直接测 TCP 往返，数字才有意义。**

绕开代理之后，本机到 `rpc.monad.xyz` 的往返中位数是 **303 ms**（8 次采样，280 到 313）。在这条路上找不到更近的节点，换端点解决不了问题。

## 流水线化能救，但不该做

现在的顺序是串行的，`read(249) → decide(325)`，合计 574 ms。如果让第 N+1 块的读盘口在第 N 块的模型推理还没结束时就开始，理论上能压到 `max(249, 325)` 约 325 ms，决策率直接翻倍到九成左右。

但这会破坏一个核心保证：**第 N 块挂出去的订单必须是基于第 N 块的盘口**。流水线之后，订单可能基于一个已经过期的盘口挂出去，而订单是要在特定区块落链的，post-only 挂单的价格前提就不成立了。

作者刻意没有这么做，这是设计权衡，不是疏漏。

## 两个跳点在哪

574 ms 里几乎全是网络，那就得问清楚：这两次往返到底跨了多远。

| 环节 | 端点 | 解析到的地址 | 位置 | 本机往返中位数 |
|---|---|---|---|---|
| 读盘口 | `rpc.monad.xyz` | `198.13.133.100` | 日本东京，TeraSwitch | 303 ms |
| 模型推理 | `api.typesafe.ai` | `44.227.31.201` | 美国俄勒冈州 Boardman，AWS us-west-2 | 239 ms |

把上面那张耗时表按「服务端处理」和「网络」拆开：

| 环节 | 本机总耗时 | 服务端处理 | 网络 |
|---|---|---|---|
| 读盘口 | 249 ms | 约 18 ms 解码 | 约 231 ms |
| 模型推理 | 325 ms | 约 86 ms 推理 | 约 239 ms |

网络合计约 470 ms，占整个循环的 **82%**。

两个结论从这里直接读出来：

**一、两跳是跨太平洋的。** 一次决策在日本和美国西海岸之间各走一个来回，加上本机所在的位置，单次决策的物理距离是决定性的。

**二、模型那一跳和链那一跳一样贵。** 231 ms 对 239 ms，几乎相等。之前所有讨论都集中在「读盘口慢」上，而实际上**模型端点也是一个等量齐观的延迟来源**，把模型换到近的端点，收益不会比换 RPC 小。

## 换链或者换场所能解决吗

不能。而且币安从这台机器根本连不上。

先把各处的往返放在一起，同一套测法（绕开代理，8 次采样取中位数）：

| 端点 | 往返中位数 | 结果 |
|---|---|---|
| 东京，Monad RPC | 303 ms | 200，正常 |
| 俄勒冈，TypeSafe AI | 239 ms | 正常 |
| Hyperliquid 接入点 | 224 ms | 正常 |
| 币安接入点 | 245 ms | TCP 握手成功，HTTP 不返回 |
| 新加坡，GitHub（对照） | 251 ms | 200，正常 |

两个读数：

**一、本机到任何国际域名的往返地板是 220 到 300 ms。** GitHub 是 251 ms，Google 直接超时，Monad 反而是这批里最慢的一个。**没有「更近的场所」这个选项。**

**二、币安不通。** TCP 能连上（解析到 CloudFront 接入点），但拿不到任何 HTTP 响应，直连和走代理都一样。所以「换币安会不会快」，在这台机器上先要解决「能不能连上」。

需要说明的是，Hyperliquid 和币安这两行测到的是域名解析出的接入点，不是撮合端本身。真实端点只会更远，不会更近，所以这个对比对结论是偏保守的。

再往下一层看，换场所换掉的是**竞争**，不是距离：

| 场所 | 结构 | 你要面对什么 |
|---|---|---|
| Monad 加 Kuru | 300 ms 区块的链上订单簿，新兴链，盘口浅 | 竞争稀疏，而且作者在东京，读盘口只有 18 ms |
| Hyperliquid | 官方文档公布，同址客户端下单的端到端延迟中位数 **0.2 秒**、p99 约 **0.9 秒**（端到端指从发出请求到收到已提交响应） | 就算把进程搬到验证者隔壁，一次下单往返也已经吃掉整个 300 ms 预算，「每 300 ms 决策一次」这个节拍根本不成立；做市对手是 HLP 金库和专业做市商 |
| 币安 | 中心化撮合，同机房参与者是亚毫秒级 | 挂单的排队位置直接由延迟决定，你永远排最后，而且本机连不上 |

这个项目能在 Monad 上跑通，靠的不是 Monad 网络快，而是作者人在东京、离 RPC 只有 18 ms，加上 Kuru 是一个竞争稀疏的年轻订单簿。这两条都复制不到别的场所。

## 结论

**代码是对的，位置是错的。**

- 本地环境适合做功能验证：链路通、能真实调用模型、能出决策、dry run 安全。43.5% 的决策率足以证明整条链路是通的。
- 想看它本该有的样子，看 README 接口一节里那个已部署实例。
- 真要跑满 300 ms，**唯一的办法是把进程放到离链近的地方**，也就是一台和 Monad RPC 同区域的主机，把两段往返各压到十几毫秒量级。这正是 `READ_RPC_URL` 这个配置项存在的意义。

按上面的拆解估算，搬到东京的效果：

| 部署位置 | 读盘口 | 模型推理 | 循环合计 | 对 300 ms 预算 |
|---|---|---|---|---|
| 本机（现状） | 249 ms | 325 ms | 574 ms | 超出一倍 |
| 东京，模型仍在俄勒冈 | 约 18 ms | 约 325 ms | 约 290 ms | 刚好进预算 |
| 东京，模型也换到亚洲 | 约 18 ms | 约 95 ms | 约 113 ms | 余量充足 |

**模型部署的位置和链同等重要**，网络占了整个循环的 82%，只换链那一跳只能把预算将将填平，两跳都换才有余量。

## 复现

启动，指定端口和模型：

    MODEL=jev DRY_RUN=true PORT=3000 bun run src/index.ts

从快照里看比例：

    curl -s http://127.0.0.1:3000/ | jq '.latest.totals'

实测区块间隔：

    curl -s -X POST -H 'content-type: application/json' \
      -d '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}' \
      https://rpc.monad.xyz
